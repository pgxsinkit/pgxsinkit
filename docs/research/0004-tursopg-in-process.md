# TursoPG as an in-process pgxsinkit client database

Assessed on 25 November 2026 against Turso main at `4f61bc742f35d7ebeb0a91d7125253dbb977f8d9`, committed at 10:02 UTC. This is a source and upstream-development assessment. No Turso builds, device tests, correctness qualification or performance measurements were run for this investigation. The scope is an app-local database embedded in the application's process on Linux, iOS and Android. [Assessed commit](https://github.com/tursodatabase/turso/commit/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9)

## Assessment

TursoPG is a credible medium-term candidate for an additional native client engine. Upstream already exposes PostgreSQL execution as an in-process Rust library and exercises that path in its conformance suite. The main uncertainty is whether its evolving PostgreSQL semantics cover pgxsinkit's actual client workload with adequate durability, followed by the work of exposing that library through native application bindings. A calendar estimate for upstream readiness would exceed the available evidence. [Rust frontend](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/frontend/lib.rs), [embedded conformance backend](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/testing/sqltest/src/backends/tursopg_embedded.rs), [compatibility reference](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/COMPAT.md)

## What upstream already provides

The embeddable frontend is a workspace crate named `turso_pg`. On 25 November its crates.io index entry returned 404, while the entries for `turso`, `turso_core` and `turso_pg_parser` resolved. An experiment can build the frontend from a pinned Git revision. [Frontend manifest](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/frontend/Cargo.toml), [crates.io sparse index entry](https://index.crates.io/tu/rs/turso_pg)

The `turso_pg` crate exposes database opening, per-connection PostgreSQL session state, prepared statements, value binding, row stepping, structured errors with SQLSTATE, statement interruption and resumable I/O. `open_database` selects `PostgresDialect`, initializes the catalog and enables MVCC. `PgConnection::connect` installs PostgreSQL session hooks and transaction state. Calling the generic core connection directly would bypass part of that behavior. The embedded SQL-test backend shows how to call these APIs within the host process. [Opening and connection API](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/frontend/session.rs), [statement API](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/frontend/statement.rs), [error API](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/frontend/error.rs)

Its architecture compiles PostgreSQL SQL through a frontend into the engine's bytecode interpreter. The parser currently depends on `pg_query` 18.1 and its C PostgreSQL parser dependency. Native integration therefore includes cross-compiling that dependency. The source establishes an embedding path without requiring a server process or PostgreSQL wire protocol. The interpreter architecture is compatible in principle with iOS execution restrictions, but this assessment has not verified an iOS build of the PostgreSQL frontend. [Architecture and parser](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/COMPAT.md), [parser manifest](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/parser/Cargo.toml), [workspace dependencies](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/Cargo.toml)

Turso already has React Native bindings with a local-only database mode, native iOS device/simulator builds, Android builds for four architectures and platform packaging in CI. The Android bridge requests a 16 KiB maximum ELF page size. These provide reusable platform groundwork. The present SDK kit depends on `turso_sqlite` and constructs `SqliteDialect`, and its mobile CI builds that SDK. Extending the bindings to PostgreSQL requires routing operations through `turso_pg` session and statement APIs, preserving typed results, errors, cancellation, rollback and close cleanup. Existing SQLite mobile artifacts establish core portability, while PostgreSQL mobile qualification remains work to do. [React Native API](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/bindings/react-native/README.md), [SDK implementation](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/sdk-kit/src/rsapi.rs), [mobile CI](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/.github/workflows/react-native.yml), [Android linking](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/bindings/react-native/android/CMakeLists.txt)

## PostgreSQL maturity

The declared compatibility target is PostgreSQL 18. Upstream marks PostgreSQL support experimental. Current support includes ordinary SELECT/JOIN/subqueries, CTEs, DML with RETURNING, schemas and search paths, savepoints, primary/unique/check constraints, arrays, custom types, enums, UUIDs, timestamps, JSON and partially emulated catalogs. The compatibility reference documents many limitations within these categories, so a supported category cannot establish complete behavioral equivalence. [Compatibility reference](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/COMPAT.md)

The following differences are particularly relevant when evaluating an embedded client engine.

- `CREATE FUNCTION`, `DO`, PL/pgSQL and PostgreSQL `CREATE TRIGGER` remain unsupported on the assessed main. `LISTEN`/`NOTIFY` and advisory locks are unsupported. A client relying on these needs an implementation decision for each behavior. [Functions, triggers and backend features](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/COMPAT.md)
- Transactions use snapshot isolation corresponding to REPEATABLE READ. Other explicitly requested isolation levels are rejected. A statement error aborts the transaction block and savepoints can recover it. [Transaction support](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/COMPAT.md)
- Foreign-key declarations are accepted while enforcement is disabled on PostgreSQL connections. Open PRs #10922 and #11346 address this, and the larger proposal also identifies core FK counting bugs exposed by enabling it. [PR #10922](https://github.com/tursodatabase/turso/pull/10922), [PR #11346](https://github.com/tursodatabase/turso/pull/11346)
- Type and coercion gaps can alter values, comparisons or reported result types. Examples recorded in main include boolean text/array output, array values crossing subqueries, incomplete type propagation for expressions and numeric conversion/precision differences. An open issue also records enums comparing by their stored text. These affect correct synchronization and queries as well as ORM result decoding. [Types and recorded differences](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/COMPAT.md), [array gap cases](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/conformance/pg-sqltests/gaps/arrays.sqltest), [enum ordering issue #10444](https://github.com/tursodatabase/turso/issues/10444)
- JSONB operator semantics and type preservation remain incomplete. ALTER TABLE supports a restricted set of changes and one subcommand per statement. Binary text ordering accepts `COLLATE "C"`, POSIX and a small set of binary collations. [JSON, DDL and collation reference](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/COMPAT.md)

Upstream's curated SQL corpus runs through the embedded backend and against PostgreSQL 18. It deliberately permits documented divergences using `@compat-gap` expectations. At the assessed commit, there are 555 such annotations across the PostgreSQL and shared corpora. Its broader PostgreSQL regression runner lists 103 test scripts, with `comments` the sole script requiring byte-exact PostgreSQL output and 102 scripts marked as known-different. These counts describe the checked-in test policy and broad scripts containing many statements. They cannot be interpreted as a percentage of application queries failing. SQLSTATE differential fuzzing is currently manual because expression typing, overload resolution and overflow still diverge. [SQL-test CI](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/.github/workflows/sqltest.yml), [regression policy](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/conformance/run.py), [gap corpus](https://github.com/tursodatabase/turso/tree/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/postgres/conformance/pg-sqltests)

## Expected native benefits

The in-process Rust path avoids the WebAssembly execution boundary and can use the host's filesystem directly. It is reasonable to expect opportunities for reduced startup cost, fewer copies and lower memory use on supported native applications. SQL still goes through the PostgreSQL parser and translator, and the optimizer, value representation, MVCC and host-language bridge all contribute to actual cost. Neither upstream's general performance documentation nor the inspected benchmark tree establishes a TursoPG-versus-pgwasm result for pgxsinkit's workload. No performance multiplier is justified by this investigation. Measure batched sync application, representative indexed reads and joins, transactions, cold opening, steady RSS and bridge cost on the intended devices. [Engine architecture](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/README.md), [performance harnesses](https://github.com/tursodatabase/turso/blob/4f61bc742f35d7ebeb0a91d7125253dbb977f8d9/PERF.md)

## What pgxsinkit needs from the local database

Reviewed against pgxsinkit commit `74a3d8a`. A TursoPG backend would keep the registry, Circuits stream reader, envelope decoding and fold, and mutation transport. It would change local execution, storage lifecycle, and the implementation of some SQL-generated behavior.

| Area                         | What runs in pgxsinkit today                                                                                                                                                                                                                                                                                                 | Implication for TursoPG                                                                                                                                                                                                                                                                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sync boot and lifetime       | Every start provisions both durable and `pg_temp` cursor/tag tables, even with sync disabled. Ephemeral groups also create TEMP tables and, for writable groups, TEMP sequences, functions and views. Writable registries create a TEMP mutation-status view even with only persistent groups.                               | TEMP support blocks stock read-only startup too. A scoped prototype can gate session metadata when it only supports persistent groups. A production implementation has to preserve the session boundary, including cleanup after a crash and account switches.                                                                                |
| Applying stream changes      | One transaction applies rows, writes all acknowledged shape offsets, and rolls back on unsubscribe. It uses custom `SET LOCAL`, keyed upserts and `TRUNCATE` or scoped deletes on refetch. Every nonempty batch of deletes uses `DELETE … USING json_to_recordset(…)`.                                                       | Transactions, custom settings and upserts are promising on main. `DELETE … USING` is rejected, so even simple read-only schemas need a transactional, bounded keyed delete path. Qualify refetch separately because TursoPG lowers `TRUNCATE` to DELETE.                                                                                      |
| Initial snapshots            | The registry selects COPY, JSON recordsets or parameterized INSERT. COPY passes bytes straight to pgwasm via `/dev/blob`; TursoPG currently reads COPY input from a host path.                                                                                                                                               | Start with prepared, bounded batches. Upstream's existing `json_to_recordset` is promising for scalar data, but expects a PostgreSQL array literal for array-typed fields where the existing producer can send JSON arrays. Add a native bulk entry point only if throughput justifies it.                                                    |
| Offline mutations and events | Writable projections generate PL/pgSQL reconciliation functions and multi-event triggers, read-model views, journal sequences, and a JSONB outbox. The reconcile trigger clears acknowledged overlays only when the right server version arrives, and retires earlier conflicts before clearing the resolving journal entry. | This is the largest feature gap. One path is to run reconciliation explicitly inside the same local apply transaction, sharing the existing predicates with the client recovery path. Cover every source of writes that used to fire the trigger. Plain `LANGUAGE sql` function support does not provide this behavior.                       |
| Live queries                 | pgwasm discovers dependencies through PostgreSQL catalogs and uses statement triggers, `pg_notify` and temporary state. pgxsinkit already has application-side registration, coalescing and diff handling for subscribers.                                                                                                   | Supply the same live-row contract from committed writes through the native adapter, initially with a single owned writer and coalesced reruns. A rollback emits no refresh. Unknown write dependencies can invalidate all active queries initially. Reusing the pgwasm live implementation as-is would require the missing database features. |
| Drizzle and app queries      | PostgreSQL query builders assume native parameter types, positional/object rows, row counts and the current codecs. Registries can use UUID, JSONB, exact numeric, enums, arrays, `bytea` and dates/timestamps. Enum bootstrap uses a catalog check inside a `DO` block.                                                     | Test values and errors, not just whether SQL parses. Keep bigint, numeric and temporal precision, distinguish SQL NULL from JSON null, and verify ordering and equality. Gate supported types and query features by actual differential fixtures. Enum creation needs its own idempotent path if `DO` remains unavailable.                    |

## Integration boundary

The declared [store factory](../../packages/client/src/store-engine.ts) and [worker factory](../../packages/client/src/worker/define-sync-worker.ts) provide injection points, but their contract is `PgwasmClient`, including `live`, storage and build identity. [Build permanence](../adr/0063-build-permanence-and-storage-build.md) and the [registry config](../../packages/contracts/src/config.ts) currently enumerate `c` and `pgrust`. The direct `pgwasmInstance` path expects the caller to provision schema and skips the managed outbox. Use the existing SQL-executor boundaries where practical, then give native storage its own identity and lifecycle. pgwasm's filesystem seam, raw `PGDATA` archive and `pg_dump` helpers are specific to its build.

The small native boundary is open, parameterized queries and batch execution, a pinned connection per transaction, row/error codec, commit notifications, and close/delete. Keep the database off the UI thread and batch calls over the JS/native boundary. Linux can qualify this through a Bun native addon. A React Native app needs the PG-facing native binding, its app-private paths and lifecycle, and a runtime check of the toolkit paths it will actually use. The browser-specific worker placement, Web Locks and OPFS do not belong in a native adapter. Existing replicated rows can be rehydrated into a fresh store. Any future engine-switch flow also has to account for unsent mutations and outbox events, which a resync alone cannot reconstruct.

## Qualification and decision

1. **Linux spike now.** Pin upstream and use the actual in-process frontend. Run a persistent read-only registry fixture through fresh snapshot, streamed insert/update/delete, cursor commit and reopen. Cross-check a representative Drizzle query set, row/offset state, and error behavior with the current PG19 client. Use deliberate capability checks for SQL outside the fixture. This proves an opt-in backend for a defined workload if it passes.
2. **Early mobile build.** Cross-compile the same PG frontend and bridge for physical iOS and Android devices. Prove cold start, app background/resume, process kill around COMMIT and checkpoint, full disk/write errors, and reopen. Check that acknowledged local writes and offsets recover together. Current mobile artifacts and Linux embedded SQL conformance de-risk different parts of this work.
3. **Promote only after app-level parity.** Extend to a writable registry with overlay convergence, journal recovery, outbox and live subscriptions. Check revocations and ephemeral teardown against retained data. Existing pgxsinkit tests provide behavioral cases for [sync apply](../../tests/unit/sync-apply.test.ts), [ephemeral schema](../../tests/unit/ephemeral-schema.test.ts), [convergence](../../tests/unit/convergence.test.ts), [outbox](../../tests/unit/event-outbox-append.test.ts), [live rows](../../tests/unit/live-query-manager.test.ts) and [registry roundtrip](../../tests/integration/registry-sync-roundtrip.integration.test.ts).
4. **Measure on the target.** Compare cold open, resident/peak memory, shipped bytes, uncached and warmed local queries, live refresh, snapshot throughput, steady-state applies and commit latency at equal durability. Native execution can remove WASM startup, linear-memory and wire-codec costs. Frontend translation, bridge copying, checkpoint costs and a slower bulk-load path could eat that gain.

A scoped native option for known registries is a credible mid-term goal. A transparent option for current arbitrary registries would take either substantial upstream semantic support or deliberate pgxsinkit refactors with equivalent guarantees. PG18 upstream conformance is a signal of progress; the actual compatibility target for this integration is the pgxsinkit workload on PG19. This was a source review. No TursoPG build, device run or benchmark was performed.
